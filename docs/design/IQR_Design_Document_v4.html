Design Document · v4 · Cloud-Native Agentic Architecture

IQR — Intelligent Quality Review

An agentic AI platform that validates internal-control evidence packages end to end and emits a cited, audit-ready pack. Agents reason; deterministic tools compute; a frozen, expert-approved plan governs every run; humans hold both gates. Designed for any organization operating a controls program (SOX 404 or equivalent), deployable from a git clone to a corporate workstation, with Azure AI Foundry as the managed intelligence layer.

01The three laws

Every design decision descends from three laws. When a choice conflicts with one, the choice loses.

1 · Numbers are computed by deterministic code, never by a model. A test fails if a model is invoked on any numeric path. Models decide where an answer lives and what it means — never what a number is.
2 · Every claim carries a resolvable evidence locator. A verdict sentence without a citation that mechanically dereferences against hashed evidence cannot exist in the output. This is enforced by a gate, not a convention.
3 · Same input produces the same verdict. Same package + same plan version ⇒ identical verdict and evidence set, replayable from the ledger.

02What it validates

Each period, a control performer uploads an evidence package to the GRC system. A human reviewer then re-performs the control against that evidence by hand. IQR automates the re-performance between two artifacts:

Input — the evidence package. A nested tree, three to six levels deep: a control process document (.docx), workbooks (.xlsx/.xlsm/.xlsb) including macro-enabled and binary formats, approval emails (.msg/.eml) whose attachments contain ZIPs holding further workbooks and reviewer checklists, screenshots embedded inside workbook tabs and documents, spreadsheet workbooks embedded as OLE objects inside documents (observed at 184 MB), and document-management links standing in for files.

Output — the audit-ready pack. One downloadable archive: a verdict per check pass pass with gaps fail, the auto-completed reviewer checklist, an artifact manifest with the hash of every leaf validated, an explicit gaps-and-observations register, and a citation for every claim — down to the exact cell (Recon!B30339), email line (msg-id · line 1), or screenshot region.

The four check modalities (every control decomposes into these)

ModalityWhat it assertsExample from the validated corpus
Numeric recompute Totals, deltas, products re-derived from cells and compared under a tolerance Consolidated trial-balance deltas net to zero (real deltas are ~1e-06 floating-point residue — tolerance-based comparison, never ==0)
Temporal ordering Timestamps normalized across timezones, then ordered Certified report run (in-cell stamp, GMT) must precede reviewer approval (email header, CDT) — the plan pins which stamp anchors the check
Vision tie-out Screenshot evidence exists and its provenance matches; labeled values tie to workbook cells BI-portal screenshots prove the certified source; numeric ties come from certified workbook cells — small-font OCR digits are never trusted for arithmetic

The reviewer checklist that accompanies each package is the human contract for the control. IQR auto-completes it: each checklist item maps to plan checks, and the pack marks it with the verdicts and citations that answer it — so the reviewer signs a completed document, not a blank one.

04Intake first — start from the evidence, not a dropdown

The real process begins with a pile of files, not a control number. A performer bulk-uploads whatever the period produced — workbooks, approval emails, ZIPs, screenshots, in any mix and nesting — and IQR works out the rest before anything runs:

  1. Ingest deterministically: the tree is unpacked, hashed, and every fact made addressable — same machinery as the run itself.
  2. Infer the control mechanically: every frozen plan version is scored by required-evidence coverage against what is actually present. The best-fitting version per control is ranked — packages from different periods legitimately match different plan versions, and intake says which.
  3. Narrate: an intake agent turns the mechanical facts into the package's story — what this appears to be, what will be validated, what is already missing (declared as future gaps up front). Every fact in the story comes from the graph and the plan; the model only phrases it.

A human confirms the inferred control before the run — inference ranks, people decide, and the frozen plan remains the law. Evidence already missing at intake is shown before a single check executes, so nobody waits on a run to learn the package is incomplete.

05The run, stage by stage

ingest ──▶ match ──▶ sentinel ──▶ check ×N (parallel fan-out) ──▶ verify ──▶ adjudicate ──▶ pack │ │ │ │ │ │ hash honest 6 adversarial numeric: pure code blinded citation gate + every "missing" detectors vision/temporal/signoff: re-perform aggregation leaf never pass (no LLM) tool-using agents from cites any fail⇒fail

The topology is fixed and versioned: it serializes to a SHA-256 signature recorded in every run ledger, so any change to the orchestration itself is a diffable, versioned event. State flows as typed structures — the Evidence Graph travels as a graph, never re-dumped into prompt text, which is both how context is maintained across the whole run and how the verifier's blindness is enforced (what an agent's input type cannot carry, it cannot see).

The Anomaly Sentinel is deliberately not an agent. The adversary must not hallucinate accusations either, so its six detectors are deterministic code, each anomaly cited: recycled prior-period artifacts · duplicate bytes under different names · link placeholders posing as attachments · pasted constants where a reconciliation formula should be · deltas parked suspiciously close to tolerance · approval emails sent by the declared preparer. High-severity anomalies become exceptions; a package can never sail through clean while carrying a placeholder where evidence should be.

How an agent is allowed to think

The agent loop is a strict protocol: the model may respond only with a tool call or a typed final conclusion, and the runtime — not the model — accumulates the citations those tools return. Every number, timestamp, and quotation in a finding is an echo of a tool result. The model runs at temperature 0 with a pinned seed through a single adapter; the ledger records which backend answered every call, so fallback (to a secondary endpoint or the offline deterministic stub) is visible, never silent. Three protocol hardenings, each earned from a real observed failure mode: every tool is presented with its exact argument signature derived from the code (a model must never guess a parameter name); a deterministic loop-breaker refuses to re-execute an identical successful call and instructs the model to conclude; and plan-pinned lookups are prefetched deterministically and seeded into the agent's observations — where a locator leaves nothing to decide, no model is asked to decide it.

Per-seat model routing — how capability grows under governance

Each seat can run a different approved model, assigned by configuration: a fast economical model on the check seats, a stronger reasoning model in the Verifier seat, a routing meta-model for design-time plan compilation. A newly approved model earns a seat through a fixed graduation: deployment added → seat routed to it → the five eval gates must pass → the assignment ships. The ledger attributes every call to its backend, so a seat change is a diffable, auditable event. In validation, a two-model configuration (economical checks + reasoning verifier) passed every gate with 100% verdict stability across batch repeats.

Extractors behind the graph builder read every artifact type deterministically: dual-pass spreadsheet extraction (values and formulas, streaming above 60 MB with an explicit truncation sentinel), binary workbook parsing, document paragraphs with embedded media and OLE children ingested recursively, email chains with nested ZIP walks, and OCR-on-demand for images. 08Human in the loop — two gates, both human-owned

Gate 1 · Design. The Plan Compiler drafts; a subject-matter expert reviews, pins tolerances, timezone semantics, and scope exclusions, and freezes the plan as versioned, immutable JSON. The runtime refuses unapproved plans. A human decides what is validated before anything runs, once per control rather than every period.

Gate 2 · Run. Three flows converge on the exception queue: sentinel high-severity anomalies, verifier disagreements, and gaps (missing or unreadable evidence, crashed checks — which abstain loudly and can never fake a pass). A reviewer adjudicates each exception in the console with the full cited context. In Shadow mode nothing auto-submits; the final approval of every package remains a human signature over a fully cited pack. Graduation from Shadow to Assist to Primary happens per control, gated by that control's measured recall, false-exception rate, and reproducibility — trust is earned in the metrics, never assumed.

09Continuous learning — and why there is no gradient in the loop

Every human adjudication is recorded with its rationale. It enters the runtime path only through two locks: the five-gate regression eval must stay green with the exemplar included, and an expert signs the release. Accepted exemplars index into the Golden Library; the next package with the same pattern retrieves how it was judged before, and every override becomes a permanent regression case. The system is forever tested against its own history — quality compounds and cannot silently drift, because drift fails the eval.

Do we need a machine-learning model on Azure for reinforcement learning? No — by design.

Reinforcement learning IS in the loop — the bandit family, not the gradient family.

Every adjudication is a reward signal: agreement with IQR's conclusion is a 1, an override is a 0. The learner updates a Beta-Bernoulli posterior per (control, check) — transparent agree/override counts anyone can read, version, and revoke. What the posterior drives is confidence and review priority: low-confidence checks surface first in the exception queue (a human's judgment buys the most learning exactly where uncertainty is highest), and high-confidence checks accumulate the evidence that justifies Assist/Primary graduation. What it never drives is a verdict — verdicts remain tools + citations + verifier. The learning pass is offline, idempotent over the adjudication journal, and its state lives beside the Golden Library in the knowledge store.

Why not gradient RL / fine-tuning — the weights would eat the evidence.

Gradient methods need orders of magnitude more reward events than a controls program produces, and each expert adjudication is too precious to dissolve into an opaque weight update. Stored as a cited exemplar plus a posterior count it is inspectable, versionable, and revocable; baked into weights it is none of those.

Fine-tuning would break the laws it serves.

Law 3 demands replayable verdicts. A fine-tuned model that shifts with each training round makes yesterday's verdict unreproducible today and gives an auditor a black box where the Golden Library gives them a readable list of precedents. Frozen plans + retrieval-augmented judgment + regression evals achieve what RLHF would promise — behavior that improves with feedback — while staying fully auditable.

What Azure ML is actually for, if ever.

Nothing in the runtime. Two bounded futures: (a) a custom OCR/layout model if screenshot evidence outgrows Tesseract — Azure Document Intelligence covers this as a managed service, no training required; (b) anomaly-detector tuning on sentinel telemetry once thousands of runs accumulate — an offline analytics exercise, behind the same eval gate as everything else. Neither justifies standing up an ML workspace today.

10Evaluation harness — five gates on every release

GateMeaningBar
Defect recallSeeded defects caught (altered totals, inverted timestamps, missing sign-off, preparer = reviewer, screenshot mismatch)100% of seeded classes
False-exception rateClean checks wrongly flagged — reviewer trustBounded, tracked
Citation validityEvery claim's locator resolves100% — hard gate
Abstention correctnessMissing evidence declared, never invented100%
ReproducibilityIdentical verdict + evidence set across repeat runsExact

The same harness gates model changes, plan amendments, and Golden Library releases — and it runs in batch mode: N repeats scored per gate (mean/min/max) plus a per-check confidence level earned from verdict stability across the batch (HIGH / MEDIUM / LOW). Confidence is measured frequency, never model self-report. Batch scoring is also the diagnostic instrument: in validation it isolated a single unstable check, the trace named the exact cause, and after the fix the batch reported every gate passing on every run with every check at 100% stability — on a live two-model configuration. When variance does occur, it shows up as extra honest gaps routed to humans: the architecture converts model uncertainty into reviewer workload, never into false assurance.

12Productionization path — from git clone to governed deployment

The repository is the deployable unit: clone, create a virtual environment, install, run the offline test suite (green with no keys at all), add endpoint configuration, serve. The same sequence works on any corporate workstation; the deterministic stub keeps development and CI fully offline.

Security ladder — Easy Auth now, least privilege at production

  1. POC (now): platform authentication (Easy Auth) on the console — tenant sign-in required, no anonymous access; secrets in a gitignored env file; loopback-only when run locally.
  2. Pilot: managed identities replace every key — the app and MCP server authenticate to storage, Search, and Foundry by identity, and the env file holds no secrets; Key Vault for anything that must remain a secret; role-based access with three roles: Reviewer (run, adjudicate, download), SME/Approver (plan approval, exemplar release), Admin (deployments, configuration). Plan approval and exemplar release require the approver role — the software enforces the same segregation of duties it audits.
  3. Production: private endpoints on storage and Search; WORM immutability on the evidence container; diagnostic logs to a log workspace; the run ledger retained as the platform's own ITGC evidence; per-control graduation gates reviewed with internal audit.

13Roadmap

  1. Shadow — runs beside the human reviewer; results compared; nothing auto-submits. (Current mode.)
  2. Assist — IQR drafts every finding; the human decides each one. Gate: measured recall, precision, reproducibility on that control.
  3. Primary — IQR decides; humans review exceptions and samples. Per-control gating; each control advances only as fast as its demonstrated accuracy.

Near-term engineering: bulk evidence migration to the cloud store; console deployment with platform auth; connectors for mailbox and document-management pull behind the existing resolver interface; a parsed-artifact cache keyed by content hash for ingest speed at scale.

Grounding for this document: the v1–v3 design documents and build handover; real-corpus validation across three production-shaped controls (consolidation reconciliation, external-report review, rebate calculation — 3.4M cells, 245 images, six-email sign-off chains, a 184 MB embedded workbook); the working codebase (50 passing invariant tests); and live five-gate eval passes on the deployed Foundry model seat. All identifiers generic by intent — the architecture is organization-agnostic.
